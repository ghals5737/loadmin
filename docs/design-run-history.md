# 설계안 — 테스트 히스토리 저장/비교 (Phase 2-2)

상태: 구현 완료 · 2026-08-20

## 1. 문제

run은 `LoadTestRunRegistry`에 인메모리로만 남고, 최근 20개만 유지되며, 앱을 재시작하면 사라진다.
그래서 "튜닝 전후로 p95가 어떻게 변했나" 같은 질문에 답할 수 없다.
부하테스트는 절대값보다 **변화**를 보는 도구인데 그 변화를 볼 수단이 없었다.

## 2. 결정

- **파일 저장** — 인메모리로는 재시작을 못 넘긴다. "어제 대비" 비교가 되어야 이 기능이 의미가 있다.
- **자동 델타 + 히스토리 목록 둘 다** — 자동 델타는 아무것도 안 해도 눈에 들어오고,
  목록은 임의의 두 run을 직접 고를 수 있게 한다.

## 3. 저장 구조

run 하나당 JSON 파일 하나, `<startedAtMillis>-<id>.json`.

- 파일명이 시간순으로 정렬되므로 별도 인덱스 없이 목록·삭제 순서가 정해진다.
- id로 파일을 찾을 때도 접미사 매칭이면 된다.
- 임시 파일에 쓰고 `Files.move`로 옮긴다 → 쓰다가 죽어도 반쯤 쓰인 JSON이 남지 않는다.
- 저장 내용은 `RunView` 전체(요약 + 초 단위 타임라인 + 서버 메트릭). 300초 run도 수십 KB.

디렉토리 기본값 `.loadmin/history`, 보관 개수 기본 100개(초과분은 오래된 것부터 삭제).

## 4. 실패해도 부하테스트를 망치지 않는다

히스토리는 편의 기능이지 부하테스트가 실패할 이유가 아니다.

- `RunHistoryStore`의 모든 IO 실패는 로그만 남기고 삼킨다.
- 엔진의 완료 콜백도 `RuntimeException`을 잡아서 run 상태에 영향을 주지 않는다.
- 읽을 수 없는 파일(구버전 포맷, 부분 기록)은 건너뛰고 나머지 목록을 정상 반환한다.

## 5. 비교 대상 선정

"같은 엔드포인트를 **같은 부하로** 때린, 이 run보다 먼저 시작한, 완료된, 요청이 1건 이상인 run 중 가장 최근 것."

같은 엔드포인트의 기준은 **HTTP 메서드 + 매핑 패턴**이다. 경로 템플릿은 다를 수 있다
(`${int(1,20)}` → `${int(1,100)}`으로 넓혀도 같은 엔드포인트를 때린 것은 맞으므로 비교 가치가 있다).

**부하 조건(동시 사용자 수)은 같아야 한다** (2026-09-10 추가). 레이턴시는 부하의 함수라서,
5 users run 다음 40 users run을 자동 비교하면 "p95 +205% 악화"로 뜬다. 원인은 부하를 8배 준 것인데
화면은 리그레션처럼 읽힌다. duration은 달라도 된다 — p95·RPS는 총량이 아니라 비율이다.

부하가 다른 run끼리 비교하고 싶으면 히스토리 목록에서 직접 두 개를 고르면 된다.
그 화면은 양쪽 부하가 다 보이고, 다를 경우 경고 문구가 붙는다.

`GET /loadmin/api/runs/{id}/baseline`은 registry의 살아있는 run을 먼저 본다.
run이 끝난 직후 UI가 바로 물어보는데, 자기 파일이 아직 안 떨어졌을 수 있기 때문이다.
비교 대상이 없으면 204.

## 6. API

| 메서드 | 경로 | 응답 |
|---|---|---|
| GET | `/loadmin/api/history` | `HistoryEntry` 목록 (최신순, 타임라인 제외) |
| GET | `/loadmin/api/history/{id}` | 저장된 `RunView` 전체 |
| GET | `/loadmin/api/runs/{id}/baseline` | 비교 대상 `RunView`, 없으면 204 |

`loadmin.history.enabled=false`면 store 빈이 없고 컨트롤러도 등록되지 않는다.
UI는 `/loadmin/api/history`의 404를 "히스토리 꺼짐"으로 읽고 섹션을 숨긴다.

## 7. UI

- **run 화면**: 끝나면 요약 카드 아래에 `vs previous run (39s ago, 5 users): p95 101ms +57ms / +130% (was 44ms) …`.
  좋아졌는지 나빠졌는지는 지표마다 다르므로(p95는 낮을수록, req/s는 높을수록 좋음) 방향을 지표별로 판단해 색을 준다.
  같은 차트에 직전 run의 p95를 점선으로 겹친다(축을 추가하지 않는다 — 같은 단위, 같은 y축).
- **엔드포인트 목록 아래 History 섹션**: 시간·대상·부하·req/s·p95·에러율. Open으로 과거 run을 그대로 다시 열 수 있다.
- **두 개 선택 비교**: 지표별 before/after/변화 표 + p95·req/s 오버레이 차트. 오래된 쪽이 항상 before.
