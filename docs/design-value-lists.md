# 설계안 — ID 목록 공급 (Phase 3-4)

상태: 구현 완료 · 2026-09-11

## 1. 문제

경로변수를 쓰는 엔드포인트를 테스트하려면 실제 ID가 필요하다.
`${int(1,20)}`은 ID가 숫자일 때만 통한다. 실사용처의 ID는 `hg240901-a123459` 형태라
지금은 이렇게 손으로 채워야 한다.

```java
@LoadTest(path = "/api/private/v1/snsb2/examinees/${pick(hg240901-a123459|hg240902-b234567|...)}")
```

엔드포인트 15개에 각각. 어노테이션이 ID로 뒤덮이고, ID가 바뀌면 코드를 고쳐서 재배포해야 한다.

## 2. 어디서 값을 받을 것인가

| 방법 | 판단 |
|---|---|
| 서버의 파일 (`.loadmin/data/ids.txt`) | 컨테이너에 파일을 넣는 일이 생긴다. dev가 ECS면 그것부터 일거리 |
| 엔드포인트를 한 번 호출해 목록을 받아옴 | 그런 API가 있어야 하고, 응답에서 값을 꺼내는 규칙이 필요 → correlation 과제 |
| **UI에 붙여넣기** | `select id from examinees limit 200` 결과를 그대로 붙이면 끝. 채택 |

## 3. 문법

이름 붙인 목록을 만들고, 기존 생성기가 `@이름`으로 참조한다.

```
ids = hg240901-a123459, hg240902-b234567, hg240903-c345678
```

```
/api/private/v1/snsb2/examinees/${pick(@ids)}     무작위로 하나
/api/private/v1/snsb2/examinees/${cycle(@ids)}    순서대로 돌며 균등하게
```

`@`를 쓰는 이유: `${pick(ids)}`는 지금도 유효한 표현이고 "ids라는 문자열 하나"를 뜻한다.
접두어가 없으면 기존 템플릿의 의미가 조용히 바뀐다.

`pick`과 `cycle`의 차이는 숫자 범위일 때와 같다 — 무작위냐, 고르게 도느냐.

## 4. 값은 저장하지 않는다

헤더와 같은 규칙이다. 목록은 **run에만 실리고 `LoadTestSpec`에는 들어가지 않는다.**
히스토리에 남는 것은 `${pick(@ids)}`라는 참조뿐, 값이 아니다.

의료 플랫폼에서 쓰인다는 걸 생각하면 이 선택은 편의가 아니라 요건에 가깝다.
수검자 ID 200개가 디스크의 JSON 파일에 남아서는 안 된다.

다만 **export한 스크립트에는 값이 들어간다.** 값 없이는 스크립트가 돌지 않기 때문이다.
생성된 파일 상단에 그 사실을 주석으로 남겨, 커밋하기 전에 생각하게 한다.

## 5. 검증

- 목록 이름은 식별자 문자만
- 목록 200개, 값 하나당 200자, 전체 10,000개까지
- PATH 모드에서는 값 하나하나가 기존 `pick` 리터럴과 같은 규칙을 통과해야 한다
  (`/ ? # & = % ; \`, 공백, 제어문자 불가) — 값이 다른 엔드포인트로 새는 길을 막는다
- 없는 목록을 참조하면 run 시작 시 400

## 6. 비목표

- DB에 직접 질의해 목록을 채우기 — 부하 도구가 DB 접속 정보를 갖는 건 과하다
- 목록을 서버에 저장/재사용 — 위 4번과 같은 이유
- 두 목록의 값을 짝지어 쓰기(같은 인덱스의 id와 name) — 필요해지면 그때
